# Discovery Report: CLO-799 — Fix the enabled-model set pinning gcm to one model

## Problem Framing

**WHO**: Any gcm user who configured a provider with the `gcm provider` wizard (CLO-516)
and later wants a newer model that the wizard did not enable. The reported case is a
`google` config pinned to `gemini-3.1-flash-lite`.

**WHAT today**: Model discovery is correct - the live Google catalog is fetched and the
wizard's candidate list contains the newer Gemini models. But the persisted enabled set
(`models = ["gemini-3.1-flash-lite"]`) is a hard allow-list that every model-bearing
surface fails closed against:

1. `enforce_enabled_model` (`src/main.rs:301-307`) rejects `--model gemini-3.5-flash-lite`
   with exit 1 and a message that lists only the *enabled* entry.
2. The wizard pre-selects the current enabled set in a `cliclack` multiselect
   (`src/config/facade.rs:216-231`). Filtering hides the pre-selected entry (cliclack only
   renders matching rows), so pressing Enter after filtering re-saves the same single
   entry. The wizard is the only remediation the error message offers, so the trap is
   self-perpetuating.
3. `ProviderId::Google.default_model()` is `gemini-3.5-flash-lite` (`src/provider/identity.rs:171`)
   but the wizard's default pre-highlight is `selected.first()`
   (`initial_default_model`, `src/config/mod.rs:703`), not the provider default, so the
   shipped default and the wizard's choice can disagree.

**WHAT we want**: The user can get from a 3.1-only config to `gemini-3.5-flash-lite`
without hand-editing `config.toml`, the rejection message names the models that are
available (not only the enabled ones), and `default_model()` agrees with what the wizard
writes.

**WHY now**: The bug was reproduced on 2026-09-16 against the live Google catalog and is
recorded in `docs/investigations/2026-09-16-clo-797-grouping-prompt-context-overflow.md`
(the "Model-name note" section). It blocks any user from adopting a newer Gemini after
they have ever run `gcm provider`.

### Locked contracts this fix must respect

`docs/designs/clo-516-interactive-provider-wizard.md` (D4, AC-6) explicitly locks the
current behaviour: *"A resolved model (from `--model` flag, per-provider env, or config
`model`) that is not in the enabled set is rejected"*, and `tests/provider.rs`
(`enabled_model_outside_set_is_rejected`, `enforcement_runs_on_clean_repo`) encodes it.
CLO-799 asks us to *decide* whether `--model` should keep being rejected; that decision
is made below.

## Baseline Score: 7/10

The whitelist infrastructure (schema, migration, canonicalization, pure helpers) is sound
and unit-tested; no rewrite is needed. The defects are isolated: one error message, one
pre-selection default, and one wizard-instruction/flow trap. Nothing below 7 because the
only required work is targeted and the surrounding tests are strong.

## Approaches

### Approach 1: Keep the gate, improve the message, fix the wizard (CHOSEN)

- Enrich `model_is_enabled`'s error with the provider's known-catalog list (the built-in
  discovery catalog that already includes `default_model()`), so the user sees which
  models exist beyond the enabled set, plus the explicit `gcm provider` route.
- Make the wizard's space-toggle contract impossible to miss: a prominent `cliclack::note`
  before the multiselect explaining SPACE toggles / ENTER saves the checked set, and an
  explicit prompt line.
- Make `initial_default_model` prefer `ProviderId::default_model()` when it is among the
  selected models, and ensure the shipped default is always a wizard candidate, so
  `default_model()` and the wizard agree.

**Pros:**
- Preserves the CLO-516 D4/AC-6 contract and its tests; no documented behaviour is
  reversed.
- Deterministic and offline: the enriched message adds no network call to the error path.
- Each piece is a pure helper or a prompt string - unit-testable and low risk.
- Satisfies all three ACs: the wizard can widen the set (AC1), the message lists available
  models (AC2), the default agrees (AC3).

**Cons:**
- `gcm --model <new>` still exits 1 until the user runs `gcm provider`; the fix is
  "reachable via the documented remediation", not "flag always wins".
- The message lists the built-in discovery catalog, not the live catalog (static by
  design - no network in the error path).

**Effort:** S
**Risk:** Low

### Approach 2: Let `--model` override the enabled set

`enforce_enabled_model` would return `Ok` when the resolved source is `ModelSource::Flag`,
leaving env/config/default sources gated, plus the message and wizard fixes.

**Pros:**
- Makes the reported repro (`--model gemini-3.5-flash-lite`) succeed immediately.
- Honours the documented precedence `flag > env > config > default` most literally.

**Cons:**
- Reverses CLO-516 D4/AC-6, which explicitly includes `--model`; requires rewriting two
  integration tests plus the CLO-516 design/README wording.
- Weakens the guard's stated purpose (block a typo'd non-chat model such as an embedding
  model); the failure then surfaces as a provider 4xx rather than a config error.
- A config-level convenience list vetoing the highest-precedence input is arguably the
  bug; but the issue's own AC2 explicitly keeps the rejection and only requires a better
  message, signalling that the gate should stay.

**Effort:** S
**Risk:** Medium (contract reversal ripples across docs and tests)

### Approach 3: Interactive auto-repair on rejection

On rejection with a TTY, prompt `Enable <model> for <provider>?` and, on yes, mutate
`config.toml` before continuing.

**Pros:**
- Removes the wizard round-trip entirely for the interactive case.

**Cons:**
- Makes a pre-flight config check mutate persisted config as a side effect; surprising and
  hard to test.
- Does nothing for `--json`/non-interactive callers, who are the ones scripted around
  `--model`.
- Larger blast radius for a bug whose core fix is three small helpers.

**Effort:** M
**Risk:** High

## Chosen Approach: Approach 1

The issue's AC2 keeps the rejection and only asks that the message name the available
models, and CLO-516's D4/AC-6 intentionally includes `--model`. Reversing that contract to
gain convenience is not worth the doc/test churn and the loss of the non-chat-model guard.
Approach 1 fixes each of the three root causes with minimal surface: the message tells the
user exactly which models exist, the wizard no longer hides the "press SPACE" contract
behind a filtered view, and the default pre-highlight matches `default_model()`.

## Discovery Debt

None. The decision in the issue's first scope bullet is resolved in favour of the
"rejection names the available models" branch; the remaining two scope bullets map
directly to the wizard fixes in Approach 1.
