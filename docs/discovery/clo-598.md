# Discovery Report: CLO-598 — Verify the gcm library from an out-of-tree consumer and lock its public surface

## Problem Framing

**WHO**: The `remem-ai` fork and any future external consumer that wants to depend on gcm as a library.

**WHAT today**: The library surface has been extracted across four slices (CLO-594 ADR, CLO-595 privacy scanner, CLO-596 provider identity + model registry, CLO-597 status resolution + config types). However, it has **never been exercised from an out-of-tree consumer**. In-package `tests/` integration tests compile inside the package: they see its dev-dependencies, its feature selection, and its module privacy. Three failure modes they cannot catch:
1. A public function whose signature names a type that is not itself public
2. A path that compiles only because the binary happens to enable a feature
3. An accidental export of commit-domain types (the specific risk this whole extraction was shaped to avoid)

**WHAT we want**: A verified, locked public surface that an external consumer can depend on without leaking internal types, and a decision on whether to publish to crates.io or stay path-dependency-only.

**WHY now**: CLO-597 merged 2026-07-30, completing the library extraction chain. The `remem-ai` fork is waiting. Without this check, the library could ship with a broken or leaky surface.

## Existing Code

### Library Surface (`src/lib.rs`)

The library exposes five public modules:

| Module | Purpose | Key Public Types |
|--------|---------|-----------------|
| `gcm::config` | Config types + pure helpers | `Config`, `ProviderConfig`, `ConflictConfig`, `AutoPolicy`, `MAX_ROUNDS_ZERO` |
| `gcm::paths` | XDG path resolution | `xdg_gcm_dir_from` |
| `gcm::privacy` | Secret scanner | `Scanner`, `SecretScanMode`, `ScanError`, `rules::RuleEngine`, `rules::vendored`, `detect::secret_ranges`, `detect::redact_secrets`, `entropy::Charset`, `entropy::shannon_entropy`, `entropy::normalized_entropy` |
| `gcm::provider` | Provider identity + model registry | `ProviderId`, `AuthMethod`, `ModelSource`, `ErrorKind`, `ProviderError`, `resolve_model_with_source`, `fetch_supported_models_with`, `FetchSource`, `ModelFetchOutcome` |
| `gcm::status` | Status report | `StatusReport`, `PathsStatus`, `ProviderStatus`, `build_report`, `print_human`, `print_provider_block`, `print_provider_section`, `locality_tag` |
| `gcm::debug` | Logging (doc(hidden)) | `Level`, `log!`, `debug_log!` macros |

### Binary-Only Facades

The following modules are **only** included in `main.rs` (the binary target), not in `lib.rs`:

- `config/facade.rs` — interactive wizard (`run_wizard`), `run_config_subcommand`
- `paths/facade.rs` — binary-specific path resolution
- `privacy/facade.rs` — `run_scan`, `gcmignore` integration
- `provider/facade.rs` — `Provider` trait, `select()`, per-provider backends (Groq, Google, OpenAI, Anthropic, Ollama, Vertex)
- `status/facade.rs` — `run_status_subcommand`
- `resolve/` — entire conflict resolution module (classify, markers, mergiraf, prompt, remote, report, validate)

### Feature Gating

The `[features]` section in `Cargo.toml`:
- `default = ["cli"]`
- `cli = ["clap", "dep:cliclack", "dep:console", "dep:ureq", "dep:sha2", "dep:which", "dep:url"]`
- `clap = ["dep:clap"]`

The `cli` feature gates: `clap`, `cliclack`, `console`, `ureq`, `sha2`, `which`, `url`.

### Commit-Domain Type Check

The types `Provider`, `ConflictHunk`, `ResolveContext`, and `Resolution` are **absent** from the library surface:
- `Provider` trait lives in `provider/facade.rs` (binary-only, not in `lib.rs`)
- `ConflictHunk`, `ResolveContext`, `Resolution` are not present in the codebase at all
- The entire `resolve/` module is only in `main.rs`

### Test Baseline

- **524 tests** pass with default features (`cargo test`)
- **126 tests** pass with `--no-default-features --lib` (library-only, no CLI deps)
- **0 failures** in both configurations

### ADR-002 Publish Decision

Decision 7 of ADR-002 states: **"Path-only for now (no publish until at least one consumer exists)."** This is documented in `docs/adrs/002-library-boundary.md`.

## Baseline Score: 8/10

The library surface is well-structured and the binary/library separation is clean. The `#[doc(hidden)]` pattern correctly hides internal helpers. The facade pattern keeps binary-only concerns out of the library. However, the surface has never been exercised from outside the package, and there is no automated check preventing commit-domain type leaks. Score: **8/10** — no rewrite needed, but verification is essential.

## Approaches

### Approach 1: Manual smoke consumer + surface audit

Create a `smoke/` directory at repo root with a minimal crate that depends on gcm by path. Manually enumerate the public surface using `cargo doc --lib` and grep for `pub` items. Verify feature combinations manually.

**Pros:**
- Simple, quick to implement
- Proves the library compiles from outside the package

**Cons:**
- No ongoing protection against regressions
- Manual surface audit is error-prone and not repeatable
- Not CI-checkable

**Effort:** S
**Risk:** Medium (manual steps can be missed)

### Approach 2: Automated surface verification + consumer test (CHOSEN)

Create a `smoke/` directory with a consumer crate that exercises the scanner, model resolution, and status report. Add a CI-checkable script that enumerates the public surface and verifies no commit-domain types leak. The smoke consumer is tested in CI.

**Pros:**
- Repeatable, automated verification
- CI integration provides ongoing protection
- Proves the library compiles and runs from outside the package
- Mechanical surface check catches regressions

**Cons:**
- Slightly more effort to set up
- Need to maintain the surface check as the library evolves

**Effort:** M
**Risk:** Low

## Chosen Approach: Approach 2

Automated surface verification provides ongoing protection against regressions and is the only approach that satisfies the AC "checked mechanically rather than by reading." The smoke consumer proves the library is usable from outside the package, and the surface check prevents future leaks.

## Discovery Debt

None. All unknowns are addressed by the chosen approach.
