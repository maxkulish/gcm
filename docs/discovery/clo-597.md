# Discovery: CLO-597 — Expose source-attributed status resolution through the gcm library

**Linear**: https://linear.app/cloud-ai/issue/CLO-597
**ADR**: [ADR-002](../adrs/002-library-boundary.md)
**Predecessor**: CLO-596 (Done, PR #48) — provider identity + model registry already in library
**Branch**: `feat/clo-597-status-res` from `main @ 056b0f1` (v0.6.0)

## Problem framing

A downstream consumer (lok, remem-ai) needs to ask "what will gcm do right now, and why" and get every key, model, and endpoint value back with the source it came from. Today `src/status.rs` (1,010 lines) is binary-only: its sole entry point `run_status_subcommand(args: &Cli)` takes a `clap` struct, and the module imports `crate::config::{self, Config}` and `crate::output::SCHEMA_VERSION`, neither of which is in the library. The attribution helpers are already env-pure (they take an `env_lookup: impl Fn(&str) -> Option<String>` closure), but they are not crate-pure — four binary-only imports block the boundary crossing. CLO-596 already moved `ProviderId`, `AuthMethod`, `ModelSource`, `resolve_model_with_source` into `gcm::provider`, so the provider dependency is resolved. What remains is `Config` (still binary-only), `SCHEMA_VERSION`/`VERSION` (binary-only, must stay), and three `ollama` pure helpers trapped in the binary's ollama backend.

### Pattern established by CLO-595/596

```
[lib] gcm  -> src/lib.rs
  pub mod privacy;     src/privacy/mod.rs     (library types)
  pub mod provider;    src/provider/mod.rs    (library types)

[[bin]] gcm -> src/main.rs
  #[path = "privacy/facade.rs"]  mod privacy;   (re-exports + binary-only)
  #[path = "provider/facade.rs"] mod provider;  (re-exports + binary-only)
```

The binary facade imports from `gcm::<module>` and re-exports, so `use crate::<module>::*` in binary code keeps working. Binary-only backends/wizards stay in the facade.

## Approaches

### Approach A: Facade split for config + status (follow CLO-595/596 pattern)

Split `config.rs` and `status.rs` into library modules + binary facades, exactly as CLO-596 split `provider/mod.rs` into `identity.rs` + `facade.rs`.

- `src/config/mod.rs` (library: types + pure functions) + `src/config/wizard.rs` (binary: cliclack wizard)
- `src/status/mod.rs` (library: structs + `build_report` + helpers) + `src/status/facade.rs` (binary: `run_status_subcommand`)
- Move `ollama` pure helpers to `src/provider/identity.rs` or a new `src/provider/ollama_info.rs` in the library
- Binary facades re-export from library

**Pros:**
- Consistent with the CLO-595/596 facade pattern — same file layout, same import strategy
- Clean boundary: library modules have zero `cli`-feature imports
- Library consumers get `gcm::config::Config`, `gcm::status::build_report`, etc.

**Cons:**
- Splits two large files (config 2,578 lines, status 1,010 lines) — more churn
- ADR-002 Decision 3 says "A file split can happen when the library surface stabilizes" — config split was deferred

**Effort:** M
**Risk:** medium (config is the largest file in the crate; splitting it touches every `use crate::config::*`)

### Approach B: In-place gating + status facade (minimal file movement)

Keep `config.rs` as a single file, add it to the library (`pub mod config;` in `lib.rs`), gate the wizard functions with `#[cfg(feature = "cli")]`. Split only `status.rs` into a library module + binary facade (since `run_status_subcommand` must stay binary-side). Move ollama helpers to the library's identity module.

- `src/lib.rs` gains `pub mod config;` and `pub mod status;`
- `src/config.rs` stays one file; wizard functions get `#[cfg(feature = "cli")]` gates; `GcmError` import gated
- `src/status.rs` → `src/status/mod.rs` (library: structs + `build_report`) + `src/status/facade.rs` (binary: `run_status_subcommand`)
- Binary `main.rs` changes `mod config;` → `use gcm::config;` (or thin facade if needed for `GcmError` mapping)
- `ollama::is_cloud_model`, `normalize_host`, `DEFAULT_BASE_URL` move to `src/provider/identity.rs`

**Pros:**
- Follows ADR-002 Decision 3's explicit guidance to defer the config file split
- Less churn — only `status.rs` is split, `config.rs` gets feature gates
- Library consumers still get `gcm::config::Config` and `gcm::status::build_report`
- Binary keeps `use crate::config::*` working via `use gcm::config`

**Cons:**
- `config.rs` in the library has `#[cfg(feature = "cli")]` blocks — slightly noisier than a clean split
- `GcmError` (binary-only) is used by wizard functions — need to gate the import or use a library error type
- Binary `main.rs` needs `use gcm::config;` instead of `mod config;` — but this is the type-identity fix ADR-002 requires

**Effort:** M
**Risk:** low (config file stays intact, only gating added; status split follows the proven CLO-596 pattern)

## Choice: Approach B

Approach B follows ADR-002 Decision 3's explicit deferral of the config file split while still crossing the boundary. The status split uses the proven CLO-596 facade pattern. The ollama helpers are small pure functions that belong in `identity.rs` alongside the other provider identity types. This minimises churn to a daily-use tool while achieving all acceptance criteria.
