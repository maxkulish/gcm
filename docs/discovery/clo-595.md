# Discovery Report: CLO-595 — Ship gcm's secret scanner as a library API consumable by other crates

**Date:** 2026-07-27
**Task:** [CLO-595](https://linear.app/cloud-ai/issue/CLO-595/ship-gcms-secret-scanner-as-a-library-api-consumable-by-other-crates)
**Branch:** `feat/clo-595-ship-gcms-secret-scanner-as-a-library-api-consumable-by`
**Baseline:** `main @ bf8e395` (v0.5.2)

## Problem framing

The downstream toolchains (`lok`, `remem-ai`, and other in-org consumers) need to reuse gcm's mature secret scanner without embedding duplicate scan logic, but today they cannot import it directly because it is entangled in the binary crate. Today, CLI entrypoints own both scanner configuration and error semantics, so an external crate cannot build a scanner from `RuleEngine` without consuming domain types from the commit/resolve flow.

Currently `SecretScanMode` and core scanner helpers (`secret_ranges`, `redact_secrets`, `merge_ranges`) are only reachable through `gcm` internals, and the abort path surfaces `GcmError::SecretDetected`, a binary-oriented error type. This prevents clean external API composition and blocks issue acceptance criteria that require a consumer-supplied env map and a compile-time test with no gcm domain types in touched signatures.

The urgency is explicit in CLO-595: the downstream consumer needs a real API now to avoid drift from the secret scanner behavior in FR-60, and ADR-002 already narrowed the library boundary and dependency model that this ticket must implement.

## Existing code

### Crate shape and dependency model

- **`Cargo.toml`** currently defines only a single `[[bin]]` target (`src/main.rs`) and no `[lib]` section.
- `clap`/`cliclack`/`console`/`ureq` are first-class binary dependencies today, so any external import of current modules drags CLI/runtime concerns.
- `src/main.rs` defines module wiring for 15 modules (`cache`, `cli`, `config`, `debug`, `diff`, `error`, `git`, `output`, `paths`, `plan`, `privacy`, `provider`, `resolve`, `status`, `ui`) and all control flow currently runs through the binary crate.

### Privacy scanner core (`src/privacy`)

- `src/privacy/mod.rs` is the public facade currently used by the CLI:
  - imports `clap::ValueEnum` and defines `SecretScanMode` with `Off/Redact/Abort`.
  - `SecretScanMode::resolve(cli)` reads `std::env::var("GCM_SECRET_SCAN")` directly when CLI mode is absent.
  - `Privacy::load` compiles vendored rules via `rules::vendored()` and wires `PathFilter` plus `RuleEngine` for scan/e2e filtering.
  - `Privacy::prepare_grouping` and `Privacy::prepare_diff` wrap scanning over `GroupingContext` and `GatheredDiff`.
- `src/privacy/detect.rs` is self-contained around detection logic:
  - public entrypoints `secret_ranges(text, &RuleEngine)`, `redact_secrets`, and `merge_ranges`.
  - two-stage matching with precise rules + generic entropy and keyword heuristics.
  - abort semantics are expressed indirectly by higher layer (`Privacy::scan_text`) rather than a dedicated scanner-specific error.
- `src/privacy/rules.rs` compiles vendored TOML via `include_str!("rules.toml")` and builds `RuleEngine` via `RegexSet` + `Regex`.
- `src/privacy/entropy.rs` defines `Charset` + normalized entropy helpers used by the generic detector.
- `src/privacy/rules.toml` is currently embedded in-tree and used by scanner functions.

### Callsites and integration points

- **Commit flow** in `src/main.rs`:
  - `run()` creates `Privacy::load(&repo, args.secret_scan)` and calls `filter_changed`, `prepare_grouping`, `prepare_diff`.
  - abort behavior and scan mode for CLI are currently coupled through binary `Privacy` API and `GcmError`.
- **Resolve flow** in `src/resolve/mod.rs`:
  - imports `Privacy` and `SecretScanMode` for hunk-level and file-level pre-egress scanning.
  - uses `privacy.scan_text` for combined and per-version hunk filtering.
- **CLI parsing** in `src/cli.rs`:
  - `secret_scan` flag is `Option<SecretScanMode>` and `SecretScanMode` comes from `clap::ValueEnum`.
- **Binary error model** in `src/error.rs` includes `GcmError::SecretDetected { count }` used by commit/resolve abort logic and CLI messaging.

### Why this is currently blocked for external use

- No library boundary exists, so external crates cannot `cargo` import only scanner primitives.
- `SecretScanMode` and scanner errors are currently defined in CLI-oriented context.
- Scanner path relies on process env and binary-only types (`Repo`, `ChangedFile`, `GatheredDiff`, `GcmError`).
- The boundary decisions in ADR-002 (clap feature-gating, publish boundary, type identity with `[lib]+[[bin]]`) are not yet implemented in code.

### Baseline score: **4/10**

The scanner logic itself is high quality and unit-tested, and module boundaries in `src/privacy/*` are clean. The low score reflects architectural coupling: there is no library target, and scanner entrypoints are not currently shape-stable for non-CLI use. A full rewrite is not required; extraction is mostly API seam work and error boundary refactoring.

## Approaches considered

### Approach A (recommended): Add minimal `[lib]` target and expose scanner API surface in `src/lib.rs`

- **Summary:** Keep existing crate layout (no workspace), create `[lib]` target and `src/lib.rs` re-exports for scanner primitives plus types that are safe for external use.
- **Pros (max 3):**
  - Lowest disruption to existing binary workflow and contributors.
  - Reuses proven scanner modules and test coverage with minimal behavior change.
  - Aligns with ADR-002 and sets a foundation for CLO-596/597.
- **Cons (max 3):**
  - Shared `Cargo.toml` means careful feature gating for optional `clap` / `cliclack` behavior.
  - Need explicit type-migration in binary imports (`crate::X` vs `gcm::X`) for identity at the seam.
  - Requires binary-only and library-only behavior separation in a single package.
- **Effort:** M
- **Risk:** Medium

### Approach B: Split library into separate crate (`gcm-core`) and keep binary wrapper

- **Summary:** Introduce workspace or sibling crate for scanner API and keep binary crate consuming it.
- **Pros (max 3):**
  - Cleaner Cargo boundaries and independent crate versioning.
  - Cleaner dependency tree for true library-only consumers.
- **Cons (max 3):**
  - Highest migration cost: broad `crate::` import rewiring and workspace reconfiguration.
  - Significant build/test/CI churn for a single scanner extraction.
  - Disruptive for a daily-used signed-commit CLI mid-task.
- **Effort:** L
- **Risk:** Medium

### Approach C: Keep code in binary and duplicate minimal scanner module for external consumers

- **Summary:** Publish/copy `gcm`'s scanner logic as a separate module outside this repo and reference from both flows.
- **Pros (max 3):**
  - Fastest immediate unblock for consumers if done in a spike.
  - Minimal changes to current binary internals.
- **Cons (max 3):**
  - Creates long-term drift risk between implementations.
  - Violates ADR direction and does not establish reusable boundary.
  - Fails to satisfy acceptance criteria for real API evolution and clean dependency control.
- **Effort:** S
- **Risk:** High

## Approach chosen

**Approach A** (in-package `[lib]` target with scanner-focused exports) is chosen because it is the minimal-disruption path, directly aligns with ADR-002, and addresses all acceptance constraints without a workspace migration.

This keeps the implementation local, lets downstream consumers call scanner APIs today, and leaves binary-only concerns (`.gcmignore` diff filtering, `Repo` wiring, commit UX) in place while fixing the env/config and abort error seam for external consumption.

## Decision details

- **Chosen approach:** Approach A
- **Why this is right for CLO-595:** It satisfies the ticket's requirement for a library-consumable scanner API in the shortest path and supports follow-on tasks by establishing the boundary used in ADR-002.
- **Discovery debt:** None (3 approaches were considered and one selected; no unresolved blockers).
