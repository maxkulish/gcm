# Discovery Report: CLO-596 — Expose provider identity and the live model registry through the gcm library

**Date:** 2026-07-28  
**Task:** [CLO-596](https://linear.app/cloud-ai/issue/CLO-596/expose-provider-identity-and-the-live-model-registry-through-the-gcm)  
**Branch:** `feat/clo-596-provider-id`  
**Baseline:** `main @ bf8e395` (v0.5.2)  
**Baseline test count:** 489 passing

## Problem framing

The downstream consumers identified in CLO-594 (lok, remem-ai, and any future model-picker UI) need to reuse gcm's provider identity and model registry without rebuilding provider names, env-var mappings, model aliases, and fallback catalog logic. Today those reusable pieces are trapped inside the binary crate because `src/provider/mod.rs` mixes the commit-shaped `Provider` trait with the transport/identity types the registry needs, and because `ProviderId` unconditionally derives `clap::ValueEnum`, making it unavailable to non-CLI consumers.

The current behavior works for the CLI, but an external crate cannot import `ProviderId`, `AuthMethod`, `ModelSource`, or `resolve_model_with_source` without also dragging in `crate::plan`, `crate::diff`, the six per-provider backends, and the entire `clap` dependency tree. That forces downstream tools to duplicate provider identity and model-list handling, which will drift as soon as a new alias or model default is added.

This work is gated and enabled by CLO-594 (ADR-002) and the CLO-595 extraction precedent. The library boundary, sync/async seam, optional `clap` feature, and `[lib]`-inside-one-package shape are already decided, so the remaining work is mechanical extraction rather than a re-architecture.

## Existing code

### Crate shape

- `Cargo.toml` already defines a `[lib]` target (`src/lib.rs`) and a `[[bin]]` target (`src/main.rs`) with `required-features = ["cli"]`.
- The `default` feature set includes `cli`, which pulls in `clap`, `cliclack`, `console`, `ureq`, `sha2`, `which`, and `url`.
- A non-CLI consumer can depend on the library with `default-features = false` and get only serde/toml/regex/tempfile/serde_json today.
- The library currently exports only `pub mod privacy;` (from CLO-595).

### Provider identity and registry (`src/provider`)

- `src/provider/mod.rs` (~1,000 lines) defines:
  - **Library candidates:** `ProviderError`, `ErrorKind`, `ProviderId`, `AuthMethod`, `ModelSource`, `resolve_model_with_source`, and the helper `env_u64`.
  - **Binary-only:** `Provider` trait, `ConflictHunk`, `ResolveContext`, `Resolution`, `select()`, `vertex_adc_probe()`, `vertex_access_token()`, the shared prompts, and the `ChatResponse` parsing helpers used only by backend impls.
  - `ProviderId` derives `clap::ValueEnum` unconditionally at line ~333 and provides the `gemini` and `google-vertex` aliases that the CLI and config file depend on.
- `src/provider/models.rs` (~446 lines) is already free of `crate::plan`/`crate::diff` references. It defines `FetchSource`, `ModelFetchOutcome`, static fallback catalogs, the live/fallback merge logic, and the injectable `fetch_supported_models_with` seam. Its default entry `fetch_supported_models` calls `super::http::get_json`.
- `src/provider/http.rs` (~500 lines) is also free of `crate::plan`/`crate::diff`. It defines `HttpRequest`, `HttpGet`, `post_json`, `get_json`, status classification, retry/backoff, and the `bad_request_detail` helper. It uses `ureq` and logs via `crate::debug_log!` (defined in the binary-only `src/debug.rs`).
- The six per-provider files (`groq.rs`, `gemini.rs`, `openai.rs`, `anthropic.rs`, `ollama.rs`, `vertex.rs`) each keep 3–5 `crate::plan`/`crate::diff` references and implement the binary `Provider` trait.

### Callsites

- `src/main.rs` imports `provider::{ErrorKind, Provider}`.
- `src/cli.rs` uses `ProviderId` directly as a `clap` flag (`--provider`).
- `src/config.rs` uses `ProviderId` and `AuthMethod` for `Config`/`ProviderConfig` and serializes them via serde.
- `src/status.rs` uses `ProviderId`, `ModelSource`, and `resolve_model_with_source` for source attribution (this is the CLO-597 consumer).
- `src/provider/models.rs` and `src/provider/http.rs` use `super::ProviderId`/`super::ProviderError` today.

### Why this is blocked for library use

- `ProviderId` is entangled with `clap::ValueEnum`, so compiling the library without the `cli` feature fails.
- `ProviderError`/`ErrorKind` live in the same file as the binary `Provider` trait and conflict-resolution types, so exporting them from the library would also expose binary-only domain types unless the file is split or heavily gated.
- `http.rs` depends on `ureq` and on `crate::debug_log!`, both of which are currently binary-only concerns.
- The `[lib]` target already exists, so the remaining blockers are purely within `src/provider`.

### Baseline score: **6/10**

The provider code is well-tested (489 tests green) and the registry already has an injectable fetcher seam, which is excellent. The score is below 7 because the extraction requires splitting a large interleaved file, making `clap` optional, and deciding how much of the HTTP helper surface crosses into the library. This is a surgical refactor, not a rewrite.

## Approaches identified

### A. In-place `cfg(feature = "cli")` split

Keep `src/provider/mod.rs` as one file, but gate the binary-only items (`Provider` trait, `ConflictHunk`, `ResolveContext`, `Resolution`, `select()`, backend prompts, `vertex_adc_probe`, etc.) behind `#[cfg(feature = "cli")]`. Make `ProviderId`'s `clap::ValueEnum` derive conditional via `#[cfg_attr(feature = "clap", derive(ValueEnum))]`. Add `pub mod provider;` to `src/lib.rs` and re-export `http`/`models`.

- **Pros:** minimal file moves; single source of truth for `ProviderId`; least churn for imports inside `src/provider/mod.rs`.
- **Cons:** the file becomes a mixture of library and binary concerns with cfg gates throughout; future readers must mentally filter by feature; compile-time tests must exercise both `cargo test` and `cargo test --no-default-features`.
- **Effort:** M
- **Risk:** medium

### B. File-level split with a binary facade (chosen)

Create `src/provider/identity.rs` for the library types (`ProviderError`, `ErrorKind`, `ProviderId`, `AuthMethod`, `ModelSource`, `resolve_model_with_source`, and shared env helpers). Keep `src/provider/mod.rs` as a binary-only facade that `pub use`s the identity module, adds the `Provider` trait, conflict types, `select()`, and the per-provider modules, and imports identity from the library target (`use gcm::provider::*` where needed for cross-crate type identity). Move `http.rs` and `models.rs` so they import from `identity` rather than `super::{ProviderId, ProviderError}`. Expose only `gcm::provider::identity`, `gcm::provider::http`, and `gcm::provider::models` from `src/lib.rs`.

- **Pros:** clean separation of library and binary code; matches ADR-002's intent that the binary imports shared types from the library target; easiest to reason about what is public API vs internal implementation; cfg gating limited to optional clap derives and the default `fetch_supported_models` entry point.
- **Cons:** more file moves than Approach A; imports in `http.rs`, `models.rs`, and the six backend files need updating; if not done carefully both crates could end up with distinct `ProviderId` types.
- **Effort:** M
- **Risk:** medium

### C. Separate `provider-core` crate in a workspace

Spin a new workspace member crate that contains only provider identity and registry code, then make the gcm binary depend on it.

- **Pros:** cleanest semantic boundary; independent versioning if the surface stabilizes.
- **Cons:** violates ADR-002 Decision 1 (library stays inside the existing package to avoid rewriting every `use crate::X`); would force a workspace root and path-dependency migration across the entire binary; significant disruption to a daily-use signed-commit tool.
- **Effort:** L
- **Risk:** high

## Chosen approach

**Approach B: file-level split with a binary facade.**

It is the best fit for the already-accepted architecture: `[lib]` inside the existing package, binary importing shared types from the library target, optional `clap`, and the `Provider` trait staying out of the library. The file split also keeps cfg gating minimal and makes the public library surface easy to audit.

## Open questions / discovery debt

1. `http.rs` uses `crate::debug_log!`, which is defined in the binary-only `src/debug.rs`. We must either export a minimal `gcm::debug` module from the library or replace those two log calls with a library-safe hook. This will be resolved in design.
2. The default `fetch_supported_models` function calls `http::get_json`, which requires `ureq`. We must decide whether to gate that default behind the `cli` feature or keep a small `ureq`-backed helper inside the library when `cli` is enabled. The public injectable seam `fetch_supported_models_with` is the library surface either way.
3. `ProviderId::parse` currently delegates to `clap::ValueEnum::from_str`. A library-safe parser must be written for the no-`clap` build while the CLI continues to use clap's derive.

All three items have concrete resolution paths and will be addressed in the design document.
