# Discovery Report: CLO-594 — Lock the gcm library boundary, the sync/async seam and the config shape (ADR)

**Date:** 2026-07-27
**Task:** [CLO-594](https://linear.app/cloud-ai/issue/CLO-594)
**Branch:** `feat/clo-594-lock`
**Baseline:** `main @ bf8e395` (v0.5.2)

---

## Problem framing

gcm is a 18,830-line Rust CLI with a single `[[bin]]` target and no `src/lib.rs`. Every module — config, provider, privacy, plan, diff, resolve — is internal to the binary. Two downstream consumers need a library boundary: **lok** (async, tokio+reqwest) needs gcm's secret scanner and config types, and a **remem-ai** memory pipeline fork needs the same. Today there is no library boundary at all: importing any gcm type drags in `cliclack` (the interactive wizard), `clap` (CLI argument parsing), and `ureq` (sync HTTP). The three decisions — crate shape, sync vs async, config seam — are interdependent and must be locked before any extraction code moves. CLO-593 (lok's Backend abstraction) is the immediate predecessor; CLO-595 (ship the secret scanner as a library API) is the first consumer.

## Existing code

### Crate structure

- **`Cargo.toml`**: single `[[bin]]` target (`src/main.rs`), no `[lib]` target. 15 direct dependencies: `clap` (derive), `ureq` (sync HTTP), `serde`/`serde_json`/`toml`, `cliclack`/`console` (interactive wizard), `regex`, `tempfile`, `sha2`, `url`, `which`.
- **`src/main.rs`**: 15 `mod` declarations (cache, cli, config, debug, diff, error, git, output, paths, plan, privacy, provider, resolve, status, ui). All modules are private to the binary crate.

### Config seam (`src/config.rs`)

- **2,530 lines** — the largest file in the crate.
- `Config` struct (line 45): `version`, `default` (ProviderId), `providers` (Vec\<ProviderConfig\>), `conflict` (ConflictConfig).
- `ProviderConfig` struct: `id`, `key`, `endpoint`, `model`, `models`, `project`, `location`.
- **Interactive wizard code** (`run_wizard` at line 483, `run_provider_wizard` at line 791) uses `cliclack` for TTY prompts. This is ~560 lines of the file.
- `apply_to_env` (line 402) bridges config values into env vars for the provider layer.
- `config_path()` (line 163), `load()` (line 196), `save()` (line 279).
- **Key insight**: Moving `Config` wholesale would drag `cliclack` into the library. The wizard functions (`run_wizard`, `run_provider_wizard`) must stay in the binary. The pure data types (`Config`, `ProviderConfig`, `ConflictConfig`) and pure functions (`load`, `save`, `apply_to_env`, `config_path`) could move to the library.

### Provider trait (`src/provider/mod.rs`)

### Baseline score: **4/10**

The codebase has zero library boundary today. Every module is internal to the binary. The config file drags in `cliclack`, the provider trait drags in `plan` and `diff`, and `SecretScanMode`/`ProviderId` drag in `clap`. ## Approaches

### Approach A: In-package `[lib]` target (recommended)

Add a `[lib]` target to the existing `Cargo.toml` that exposes a curated subset of types. The library and binary share versioning and one registry entry.

**Pros:**
- Minimal disruption: no workspace, no new `Cargo.toml`, no git-subtree or path-dependency gymnastics.
- Single `cargo publish` — one version number, one registry entry.
- The binary continues to use `use crate::config::Config` internally; the library re-exports via `pub use`.

**Cons:**
- Library versioning is tied to the binary — a breaking change in the library forces a binary version bump.
- The `[lib]` target shares the same `Cargo.toml` dependency set; optional features (`clap` as optional) need `[features]` wiring.
- Binary-internal modules (`cache`, `git`, `resolve`, `ui`) must be gated behind `#[cfg(not(feature = "library"))]` or kept as private implementation details.

**Effort:** M (medium) — add `[lib]` target, carve `pub use` re-exports, gate binary-only deps behind features.
**Risk:** Low — well-understood pattern, no build system change.

### Approach B: Workspace with separate crate

Create a `Cargo workspace` with two crates: `gcm-core` (the library) and `gcm` (the binary, depending on `gcm-core`).

**Pros:**
- Clean semantic boundary: the library has its own `Cargo.toml`, version, and dependency set.
- Independent versioning — library can break without forcing a binary release.
- The library crate can be published separately with minimal surface area.

**Cons:**
- **Disruptive**: every `use crate::X` in the binary becomes `use gcm_core::X` or a path dependency. This is a daily-use signed-commit tool — the disruption to the primary user's workflow is real.
- Two `Cargo.toml` files, two `cargo publish` steps, two version numbers to track.
- The workspace root adds a `Cargo.toml` at the repo root (or a `members` key in the existing one), which changes the `cargo` UX for existing contributors.

**Effort:** L (large) — workspace setup, crate split, path migration, CI updates.
**Risk:** Medium — disruption to a daily-use tool; the primary user must adapt to the new crate layout mid-stream.

### Approach C: Feature-gated library (hybrid)

Add `[lib]` target (like A) but use Cargo features to make `clap` and `cliclack` optional. The library feature set excludes `clap` and `cliclack`; the binary enables them.

**Pros:**
- Cleanest dependency boundary: `clap` and `cliclack` are truly absent from the library build.
- `SecretScanMode` and `ProviderId` can derive `ValueEnum` only when `clap` is enabled (via `#[cfg_attr(feature = "clap", derive(ValueEnum))]`).
- Single crate, single version, single `cargo publish`.

**Cons:**
- Feature flag wiring is verbose: every `ValueEnum` derive needs `cfg_attr`, every `cliclack` import needs gating.
- The `[lib]` target's `Cargo.toml` still lists all deps; features just make some optional.
- Test matrix expands: `cargo test --no-default-features` must pass.

**Effort:** M (medium) — same as A plus feature flagging.
**Risk:** Low — well-understood Cargo feature pattern.

---

## Approach chosen

**Approach A: In-package `[lib]` target** — with the `clap` question resolved by making `clap` an optional dependency behind a `clap` feature flag (borrowing the best idea from Approach C).

**Reason:** The issue explicitly says "no code moves under this issue" — this is an ADR, not an implementation task. The ADR must recommend a path that the implementation tasks (CLO-595+) can follow. Approach A is the least disruptive path that still creates a clean boundary. The `clap` feature-flag pattern (from C) is adopted for `SecretScanMode` and `ProviderId` because it answers the `clap` question once for both types without forcing a workspace split. The workspace approach (B) is documented as the fallback if independent versioning becomes necessary after the first extraction.

### Decision details

| Question | Decision | Rejected option |
|----------|----------|-----------------|
| Crate shape | `[lib]` target inside existing package | Workspace with separate crate (too disruptive for a daily-use tool) |
| Sync vs async | gcm stays sync; only non-transport types cross the boundary | Both converge on async (would rewrite gcm's runtime model); gcm transport behind lok's async trait (premature coupling) |
| Config seam | `Config` data types + pure functions in library; wizard (`run_wizard`, `run_provider_wizard`) stays in binary | Moving `Config` wholesale (drags `cliclack`); keeping everything in binary (no library at all) |
| `clap` question | Optional `clap` feature on the library; `SecretScanMode` and `ProviderId` use `#[cfg_attr(feature = "clap", derive(ValueEnum))]` | Binary carries wrappers (duplication); library always depends on `clap` (unnecessary dep for non-CLI consumers) |
| `Provider` trait | Stays in binary (confirmed per issue scope) | Exporting it (forces `plan` and `diff` types on every consumer) |
| Wizard | Stays in binary | Moving to library (drags `cliclack`); removing (breaks onboarding UX) |
| Registry vs path | Path-only for now (no publish until at least one consumer exists) | Publishing to crates.io (premature — no consumers yet) |

### Sync/async rationale

The handoff recommendation (middle option: gcm stays sync, only non-transport parts are shared) is adopted. The reasoning:

1. **gcm's transport is sync `ureq`** — rewriting it to async would touch every provider backend (Groq, Google, OpenAI, Anthropic, Ollama, Vertex) and the `fetch_supported_models` live HTTP path. This is a large, risky refactor of a daily-use tool with no immediate benefit.
2. **lok's `Backend` is async tokio+reqwest** — lok already has its own transport. The shared surface is the *types* (config, secret scan mode, provider ID), not the transport implementation.
3. **The seam is the type boundary** — `Config`, `ProviderId`, `SecretScanMode`, and the pure functions that operate on them are sync-agnostic. They are `struct`/`enum` definitions and `fn` that do I/O only through injected dependencies. An async consumer can use them without any async coloring.
4. **Future convergence is not ruled out** — if a later phase needs shared transport (e.g., a unified HTTP client with retry logic), that can be extracted behind a trait. The ADR records the condition: "if two consumers share the same transport implementation, extract it behind a trait."

### Config seam rationale

The library exports `Config`, `ProviderConfig`, `ConflictConfig`, `AutoPolicy`, and the pure functions (`load`, `save`, `apply_to_env`, `config_path`, `needs_onboarding`). The wizard functions (`run_wizard`, `run_provider_wizard`) and `non_tty_instructions` stay in the binary because they depend on `cliclack` and `console`. The boundary is:

```
Library (gcm-core via [lib]):
  config::Config, config::ProviderConfig, config::ConflictConfig, config::AutoPolicy
  config::load, config::save, config::apply_to_env, config::config_path, config::needs_onboarding
  provider::ProviderId, provider::AuthMethod
  privacy::SecretScanMode

Binary (main.rs):
  config::run_wizard, config::run_provider_wizard, config::non_tty_instructions
  provider::Provider trait + all backends
  cache, cli, debug, diff, git, output, paths, plan, resolve, status, ui
```
