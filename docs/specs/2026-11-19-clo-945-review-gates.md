# Spec: Fix the task-phase review gates when a reviewer CLI or pinned model is unavailable

**Created**: 2026-11-19
**Linear**: [CLO-945](https://linear.app/cloud-ai/issue/CLO-945)
**Estimated scope**: M (12 files: 11 modified, 1 new; 7 sub-tasks)

## 1. Problem Statement

The task phases run external AI reviews at three points: the spec review (`.lok/workflows/spec-review.toml`), the design review (`.lok/workflows/design-review.toml`) and the pre-PR validation (`.lok/workflows/pre-pr-validation.toml`, and the inline gate in `.claude/commands/task/phases/implement.md`). Each review must produce a real review or a clearly named failure.

In CLO-941 and CLO-942 most external reviewers did not run, and some failures were saved as reviews. The causes, verified on 2026-11-19 with opencode v2.3.2, codex-cli 0.170.0 and the installed lok:

1. **opencode flags.** Every Gemini review step and every `health_check` calls `opencode run ... --dangerously-skip-permissions` and the review steps add `--dir "$PWD"` (`spec-review.toml:24,46-49`, `design-review.toml:13,41-50`, `pre-pr-validation.toml:27,107-116`). `opencode run --help` lists neither flag. An unrecognized flag makes opencode print its help text and exit 1 ("Unrecognized flag: ... in command opencode run"). No step checks the exit status, and the only output check rejects output under 100 characters, so the help text passes as a review. Because the health check fails the same way, `gemini=false` on every run, and `design-review.toml:32` then skips Gemini outright. opencode v2.3.2 lists `--auto` (approve permissions that are not explicitly denied) and `--agent`; `--agent plan` is opencode's read-only agent and answered on Vertex (`> plan · gemini-4-hydrogen`). opencode reads repository files from the current directory without any directory flag.
2. **AI Studio provider.** Every Gemini call and health check uses `--model "google/..."` (AI Studio), and `.lok/lok.toml:28-29` configures the `gemini` backend the same way, with the model in both `model` and `args`. lok's gemini backend appends `--agent` and `--model <model>` itself and keeps a model that already has a provider prefix (`lok/src/backend/gemini.rs:583-593`), so `args` must not repeat `--model`. AI Studio is deprecated for this project. Vertex works through opencode: `opencode run "Reply with the single word: ok" --model 'google-vertex/gemini-4-hydrogen#high' --auto` returned `ok`, and an unknown variant (`#bogus`) fails with "Variant unavailable", so `#high` is a real, validated variant.
3. **Retired and missing models.** The Ollama steps pin `glm-5:cloud` (`spec-review.toml:99`, `design-review.toml:101`, `.lok/lok.toml:35`), a retired model. `ollama launch codex` without `--model` cannot run headless ("model selection requires an interactive terminal"), and bare `codex exec --oss` falls back to a 13 GB local model. The implement gate pins `codex exec -m gpt-5.4` (`implement.md:71`), which this ChatGPT account rejects, and calls a `gemini` CLI (`implement.md:79`) that is not installed.
4. **Reasoning effort is not applied.** `pre-pr-validation.toml:53` and `implement.md:72` pass `-c reasoning.effort='"high"'`. `codex exec --strict-config` rejects it ("unknown configuration field `reasoning`"); without `--strict-config` codex ignores it. The correct key is `model_reasoning_effort`. `codex exec -m gpt-6.2-sol -c model_reasoning_effort='"high"'` printed `model: gpt-6.2-sol` and `reasoning effort: high` and answered `ok`.
5. **Report headers do not match what ran.** The write steps hard-code `**Reviewer**: Gemini 3.5 Flash` and `Codex via Ollama (glm-5:cloud)` (`spec-review.toml:224,228`; `design-review.toml` write and synthesis headers), or use the primary-model default even when the fallback model ran (`pre-pr-validation.toml` `write_review` calls). `spec-review.toml` and `pre-pr-validation.toml` synthesis files have no `**Reviewers**` line.

Further defects in the same path, found by the spec review:

6. **Skipped fallback crashes the design review.** `design-review.toml:227-228` (synthesis) and `:305-309` (write step) reference `steps.claude_fallback` without `{% if steps.claude_fallback is defined %}`, and `:305` assigns its output in single quotes. While both external reviewers failed, the fallback always ran. Once one reviewer succeeds, the fallback is skipped and these references fail (the CLO-799 failure in `.pi/lessons/lok-workflow-templates.md` L1).
7. **Failure detection is a substring match.** The `claude_fallback` `when` conditions (`spec-review.toml:146`, `design-review.toml:149`, `pre-pr-validation.toml:161`) and the synthesis prompts test `'REVIEW_FAILED' in output`. A real review that quotes `REVIEW_FAILED` (as any review of this spec does) is treated as a failure. lok evaluates `when` with MiniJinja and treats an expression error as `true` (`lok/src/workflow.rs:2946-2954`).
8. **A rejected or timed-out review can still be published or pass the gate.** A validator rejection marks the step unsuccessful but keeps its raw output, and the writers check only for `REVIEW_FAILED` text, so rejected output can be written under a normal header. The design and spec reviewer steps give the child `timeout 300` inside a `5m` lok step, so lok can kill the step before the guard writes a failure. The pre-PR synthesis has no rule for zero usable reviews and its final check accepts any non-empty file, including one from an earlier run. The inline gate uses a bare `wait`, which loses each reviewer's exit status, and records `codex_validated: true` unconditionally.
9. **Health checks are unreliable.** `timeout 15 opencode run "reply OK" ... | grep -qi "ok"` ignores opencode's exit status and matches `ok` inside words such as `token`.

Further defects, found by the owner review of the revised spec (2026-11-19):

10. **An unusable report can count as a review.** The validators run `check = "min_length(200)"` and then a Haiku validator with `on_error = "pass"`. When Haiku is unavailable, lok passes the output through as valid (`lok/src/workflow.rs:998-1010`, `error_passthrough`). Placeholder text over 200 characters with no verdict therefore passes as a successful step. The inline gate has no validator at all.
11. **The `plan` agent is not read-only.** `opencode debug agents` shows that the v2.3.2 `plan` agent allows `*` and denies only `edit` outside `~/.opencode/plan/*`. With `--agent plan --auto`, Gemini ran a shell command on request (`echo MARKER-$((6*7))` returned `MARKER-42`). `OPENCODE_CONFIG_CONTENT` is ignored by the default background service. With `--standalone` and `OPENCODE_CONFIG_CONTENT='{"permission":{"*":"deny","read":"allow","grep":"allow","glob":"allow","list":"allow"}}'`, the same request found no shell tool, and Gemini still read `Cargo.toml` (tools offered: `read`, `grep`, `glob`, `skill`). `--standalone` is a global flag listed by `opencode run --help`.
12. **Model output can end a heredoc.** The writers paste model output into quoted heredocs (`spec-review.toml:224-241`, `design-review.toml:296-314`, `pre-pr-validation.toml:287`). Output that contains the delimiter on a line by itself ends the heredoc early, and the rest runs as shell. lok has a `shell_escape` filter (`lok/src/template/filters.rs:16-24`) that single-quotes a value safely.

Further defects, found by the second owner review (2026-11-19), reproduced on lok 20261107.0.2:

13. **A failing last step does not fail lok.** A writer that is the last step and exits 1 leaves `lok run` and `lok workflow run` at exit 0. lok exits 1 only when a later step depends on the failed step (`Workflow 'c' failed: step 'gate' depends on failed step(s): w`). Steps that depend on a failed `continue_on_error` step still run. The pre-PR `synthesis` step has no `continue_on_error` (`pre-pr-validation.toml:197`), so a Claude outage skips the writer and leaves no verdict file.
14. **The validator can remove the verdict after the guard.** With `replace_output = true` (all six reviewer steps), a validator answer `{"status":"pass","output":"<text>"}` replaces the step output (`lok/src/workflow.rs:720-731,2093-2101`). The shell guard runs before that, so a step can succeed with a replaced output that has no verdict, suppress the Claude fallback and reach synthesis. `phases/spec.md:64` tests `contains REVIEW_FAILED`, a substring match.
15. **The pre-PR reviewers cannot see the change.** Both pre-PR prompts tell the reviewer to "Run: git diff main...HEAD" (`.lok/prompts/pre-pr-validation-prompt.md:5`, `implement.md:44`), which a Gemini reviewer without a shell tool (defect 11) cannot do. For specification tasks the inline gate points the reviewers at `phases.design.design_doc` and `phases.plan.plan_file`, which a specification task does not have; its plan is `phases.spec.spec_file`.
16. **The design prompt does not ask for the structure the gate requires.** `.lok/prompts/design-review-prompt.md:24` asks for "a verdict ... with key findings" and no headings, and `phases/design.md:94` reads a `## 8. Actionable Feedback` section. The tracked report `docs/reviews/clo-799-design-gemini.md` has `**Verdict:**` and `###` headings, so a reviewer that follows today's prompt fails AC18.
17. **Arguments and output are not passed as data.** The prompt assembly substitutes the ticket title, description and labels with `sed` (`spec-review.toml:38-43`). A description with more than one line ends the `sed` command ("unescaped newline inside substitute pattern"), and `|`, `&` or `\` change the replacement. lok trims leading and trailing whitespace from every shell step output (`lok/src/workflow.rs:3429`, `.trim()`).

Further defects, found by the third owner review of dd1f31a7190b (2026-11-19), checked on lok 20261107.0.2 and Claude Code:

18. **A failed rerun can look successful to the spec and design phases.** Only the pre-PR workflow gets a dependent `verdict_gate` step (defect 13). In `spec-review` and `design-review` a write step that fails is the last step, so lok exits 0 while the tracked reports of the earlier run stay in place (reproduced by the owner). `phases/spec.md` then reads the old reports as the result of this run.
19. **The synthesis and fallback formats do not match the reviewer check.** The spec and design synthesis prompts end with `## Consolidated Verdict` and `## Priority Actions` (`spec-review.toml:207-210`, `design-review.toml:277-282`), and the pre-PR synthesis prompt with `## Verdict`, `## Must Fix Before PR` and `## Recommendation` (`pre-pr-validation.toml:244-263`). None has `Actionable Feedback`, so the AC18 reviewer check rejects a valid synthesis. The spec-review Claude fallback prompt asks for `## Verdict` and `## Priority Actions` (`spec-review.toml:148-166`), so a fallback that follows it fails AC18. The design-review fallback prompt already asks for `## 7. Verdict` and `## 8. Actionable Feedback` (`design-review.toml:181-204`). `phases/spec.md:72` and `phases/design.md:94` read `Actionable Feedback` from the two external reports only.
20. **A diff failure has two competing verdicts.** When the pre-PR health check writes `REVIEW_INPUT_FAILED` to the synthesis target and the zero-review writer then runs, the writer overwrites it with `NO_REVIEWS_AVAILABLE` (reproduced by the owner in a scratch workflow: no reviewer ran, lok exited 1, and the input-failure reason was lost).
21. **The Claude fallback is not read-only.** lok runs the fallback as `claude -p --output-format text [--model <m>] -- <prompt>` (`lok/src/backend/claude.rs:255-265`) and ignores `[backends.claude] args`. The project settings allow write-capable commands such as `git commit` and `git push` (`.claude/settings.json:15-30`). On 2026-11-19, `claude -p --output-format text --tools "Read,Grep,Glob" --strict-mcp-config` offered only `Read`, `Grep`, `Glob` and the server-side `advisor`, and a request to run a shell command that writes a file created no file. With `--tools` alone, the MCP servers (write-capable Linear tools among them) stayed available.

Further defects, found by the round-3 AI review of 1fdf4ba2d04b (2026-11-19):

22. **The other Claude calls are not restricted either.** The Haiku validators (`[steps.validate]` with `backend = "claude"`, `model = "haiku"`) and the synthesis steps go through the same unrestricted lok launch, and both receive model-written review text. The pre-PR synthesis prompt asks for repository grounding (`pre-pr-validation.toml:203-263`). With `replace_output = true`, a validator answer can also replace a guard's `REVIEW_FAILED:` line that is longer than 200 characters with text that looks like a review, so the failure is lost (`lok/src/workflow.rs:2093-2101`). On 2026-11-19, `claude -p --output-format text --tools "" --strict-mcp-config` offered only the server-side `advisor`, created no file on request, and ran with `CLAUDECODE=1` set in the environment.
23. **The pre-PR fallback prompt asks for a command.** `pre-pr-validation.toml:168` tells the fallback "The git diff: run `git diff main...HEAD`", which the AC26 fallback, without a shell tool, cannot do.

**Pi compatibility facts.** Pi calls the same `spec-review` and `design-review` workflows with `lok run .lok/workflows/<name>.toml` (`.pi/orchestrator/phases/spec.md:113`, `design.md:220`), and `pre-pr-validation` with `lok workflow run pre-pr-validation <design> <plan> CLO-XX` (`implement.md:218`). Pi blocks when lok exits non-zero (`implement.md:239`) and later stops on a `NO_REVIEWS_AVAILABLE` verdict (`implement.md:365`). Pi records `review_ollama: docs/reviews/clo-XX-spec-ollama.md` and `review_gemini: docs/reviews/clo-XX-design-gemini.md`. No current lok workflow writes these names: the workflows write `-spec-review-ollama.md` and `-review-gemini.md`. The one tracked file with such a name, `docs/reviews/clo-799-design-gemini.md`, came from a direct opencode run (its `**Pipeline**` line). `PHASE_CONFIG` in `.pi/extensions/orchestrate/index.ts:284` does not require `review_ollama`. Pi therefore depends on the lok exit status, the pre-PR file names and the verdict text, which this change keeps, and on no spec- or design-review file name.

**Maintainer decisions (2026-11-18, revised 2026-11-19):**

- Every review uses two external reviewers: **Codex** with model `gpt-6.2-sol` and reasoning effort `high`, and **Gemini** through opencode with model `google-vertex/gemini-4-hydrogen#high`. gpt-6.2-sol supersedes the gpt-6.2-astra named in the ticket.
- The Ollama reviewer is removed. In `spec-review` and `design-review`, the Codex reviewer takes its place.
- No step uses the `google/` (AI Studio) provider, an AI Studio API key, or a `gemini` CLI.
- An environment variable can replace a model for one run, in every entry point including the inline gate: `GEMINI_MODEL` (default `gemini-4-hydrogen#high`, always under the `google-vertex/` provider) and `CODEX_MODEL` (default `gpt-6.2-sol`).
- The Claude fallback reviewer and the synthesis steps keep their role. They change only for reviewer names, failure detection, the template guards in defect 6, the response formats in defect 19, and the read-only launch of every Claude call in defects 21 and 22.

## 2. Acceptance Criteria

- [ ] AC1: Every Codex review command in the 4 review files uses `-m "${CODEX_MODEL:-gpt-6.2-sol}"`, `-c model_reasoning_effort='"high"'` and `-s read-only`. No file passes `reasoning.effort`.
- [ ] AC2: Every Gemini review command and health check uses `opencode run` with `--model "google-vertex/${GEMINI_MODEL:-gemini-4-hydrogen#high}" --agent plan --auto --standalone` and the AC20 permission config. No task-phase file calls a `gemini` CLI.
- [ ] AC3: No file in `.lok/`, `.claude/commands/task/`, `.claude/commands/design-doc/review.md` or `.claude/templates/` contains a `google/` model string or reads `GEMINI_API_KEY`, `GOOGLE_API_KEY` or `GOOGLE_GENERATIVE_AI_API_KEY`. `.lok/lok.toml` `[backends.gemini]` has `model = "google-vertex/gemini-4-hydrogen#high"` and `args` without `--model`, `--dangerously-skip-permissions` or `google/`, including `--auto`.
- [ ] AC4: Every `opencode run` call passes only flags listed by `opencode run --help` for v2.3.2. No opencode call passes `--dir` or `--dangerously-skip-permissions` (`lok run --dir` stays valid).
- [ ] AC5: No review step calls `ollama`. `spec-review` and `design-review` run `gemini_review` and `codex_review` in parallel; the health check reports `gemini=` and `codex=`; the `claude_fallback` `when` condition and the synthesis prompts name Gemini and Codex. `.lok/lok.toml` `[backends.ollama]` has `enabled = false` and no `glm-5` model.
- [ ] AC6: Each external review step's output is either a review or exactly one line `REVIEW_FAILED: <reviewer> <model>: <reason>`, where `<model>` is the model the step attempted. The guard writes the failure line when (a) the CLI exits non-zero or is killed by its timeout, (b) the output, trimmed of whitespace, is under 100 characters, or (c) the output is help or usage text: one of the first 5 non-empty output lines is exactly `USAGE`, starts at column 0 with `Usage:` or `DESCRIPTION`, or contains `Unrecognized flag`, or (d) the output is not a usable report under AC18. The reason names the exit code or matched condition and appends at most the first 5 stderr lines joined into one line (newlines replaced by ` | `, at most 500 characters).
- [ ] AC7: Every shell step that starts a CLI (the health checks, both external reviewers, the Claude fallback and the synthesis) gives the child a timeout at least 60 seconds shorter than its lok step timeout, so the guard always runs. In the health checks the budget covers the probe and the diff preparation together. These steps set `retries = 0`, because the Claude fallback covers a failed reviewer and a retried run would not fit in the step timeout.
- [ ] AC8: The usability decision is made once, after validation, and every consumer uses it. A new `review_status` step in each workflow depends on both external reviewers and runs after their validators. It marks a reviewer usable only when its step succeeded, its output does not start with `REVIEW_FAILED:`, and that output passes AC18. It prints `usable=<N>` on its first line, then `gemini=usable|failed` and `codex=usable|failed`. `review_status` cannot fail (it ends with `exit 0`) and runs even when both reviewers failed (a step that depends on a failed `continue_on_error` step still runs). `claude_fallback` depends on `review_status`, and its `when` condition is `steps.review_status.output is startingwith("usable=0")`. A `fallback_status` step after `claude_fallback` applies the same check to the fallback output and prints `fallback=usable|failed|skipped`, using `{% if steps.claude_fallback is defined %}`. It has `continue_on_error = true`, ends with `exit 0` and sets no `min_deps_success`: lok records no result for a step that its `when` skipped (`lok/src/workflow.rs:1631-1638`), so the skipped fallback is not a failed dependency and `fallback_status` still runs. The synthesis prompt includes only reports that these two steps mark usable, and the write step uses the same results. In all three workflows `synthesis` has a `when` that reads only `review_status` and `fallback_status` and skips it when no report is usable. Every reference to `steps.synthesis` (the write step included) sits under `{% if steps.synthesis is defined %}`, and a skipped synthesis counts as `SYNTHESIS_FAILED` (AC14 c). Failure text is detected by prefix, never by substring: a real review that quotes `REVIEW_FAILED` in its body counts as a review. `phases/spec.md` and `phases/design.md` detect a failed report by a first line that starts with `REVIEW_FAILED:`.
- [ ] AC9: The write steps publish a review only from a step that succeeded, whose output does not start with `REVIEW_FAILED:`, and whose output is a usable report under AC18. This applies to the Claude fallback as well. Otherwise they write a failure report and never the rejected output. A failure report has the `REVIEW_FAILED: <reviewer> <model>: <reason>` line as its first line, then a blank line, the AC10 `**Reviewer**` header, and the stderr excerpt if any. When the step output already starts with `REVIEW_FAILED:` (the guard ran), that line is kept as is, also when the `min_length` check marked the step unsuccessful. Otherwise the reason is `check rejected output`, `not a usable report`, or `step failed` (the guard did not run). lok templates expose only `output` and `success` (`lok/src/template/context.rs:45-52`), so each reviewer step writes its stderr to `.lok/local/review-runs/<slug>/<reviewer>.stderr` and the writer reads it from there. Stale reports: the health check (the first step) removes only `.lok/local/review-runs/<slug>/`. The write step first writes every target file of the run (review, failure report and synthesis) to a temporary file under `.lok/local/review-runs/<slug>/`, and starts publication only when all of them are written. It then renames them over the targets, the individual reports first and the synthesis target last, so each tracked report is replaced only by a complete new file. All three workflows end with a `verdict_gate` step that depends on the write step, so lok exits non-zero whenever the write step fails or does not run (defects 13 and 18). Publication guarantee: a run that fails before publication starts leaves every tracked report unchanged. A rename failure during publication can leave new individual reports next to the old synthesis, and the run exits non-zero. A caller therefore takes the reports as the result of a run only when lok exited 0. `phases/spec.md` and `phases/design.md` treat a non-zero lok exit as "no AI reviews available" and read no report file. In pre-PR, a non-zero exit means that the PR is blocked, whatever the files hold; the sentinel first line of the synthesis target (AC14, AC23) only names the reason. One run per slug at a time is assumed; the workflow header comments state it, and concurrent runs for the same slug are not supported.
- [ ] AC10: The `**Reviewer**` header of every written review and failure report, and a `**Reviewers**` line in all three synthesis files, name the reviewer and the model string from the same expression the step used (for example `Gemini (google-vertex/gemini-4-hydrogen#high)`, `Codex (gpt-6.2-sol, effort high)`). No header contains `3.5 Flash`, `glm-5`, `Ollama` or `gpt-5`.
- [ ] AC11: The Gemini steps run one model only. The `GEMINI_FALLBACK_MODEL` second attempt is removed from `design-review.toml` and `pre-pr-validation.toml`. Their header comments document only `GEMINI_MODEL` and `CODEX_MODEL`, and `pre-pr-validation.toml` points to `.claude/commands/task/phases/implement.md` instead of the `.pi/orchestrator` file.
- [ ] AC12: `design-review.toml` guards every `steps.claude_fallback` reference with `{% if steps.claude_fallback is defined %}` and passes fallback output as data per AC21. Its Gemini and Codex steps emit the AC6 failure line when the health check reports `gemini=false` or `codex=false`, with the health check's reason (AC13) as the failure reason.
- [ ] AC13: The health checks set `gemini=true` only when opencode exits 0 and its output contains the word `ok` (`grep -qiw ok`), and `codex=true` when `command -v codex` succeeds. The health-check probe timeout is at least 60 seconds, and the health-check step timeout follows AC7. A `false` result carries its reason on the same line (`gemini=false: exit 124`, `gemini=false: no ok in output`, `codex=false: not installed`).
- [ ] AC14: The verdict rules are deterministic at all three workflows and at the inline gate. The write step counts the usable reports, the Claude fallback included (AC9), and applies the first rule that matches:
  - (a) Input failure (pre-PR only): the AC23 rule.
  - (b) Zero usable reports: the shell step itself, not a model, writes `NO_REVIEWS_AVAILABLE` as the synthesis verdict. In `pre-pr-validation.toml` the write step then exits 1 (it has no `continue_on_error`), and `verdict_gate` (AC9) makes lok exit non-zero (defect 13), so Pi's failure handler runs (`.pi/orchestrator/phases/implement.md:239`). In `spec-review` and `design-review` the writer exits 0, as `phases/spec.md` expects.
  - (c) One or more usable reports, but the synthesis step failed, was skipped or fails the AC25 check: the writer writes a synthesis file whose first line is `SYNTHESIS_FAILED: <reason>`, followed by the list of usable reports. In pre-PR it then exits 1, so lok exits non-zero. In spec and design review it exits 0, and the phase reads the usable individual reports, the Claude fallback report included. When the Claude fallback is the only usable report, `phases/spec.md` and `phases/design.md` take its `Actionable Feedback` section as the review feedback and name it as the source.
  - (d) Otherwise the writer publishes the synthesis.
  - The `synthesis` step has `continue_on_error = true` in all three workflows, so a Claude outage still reaches the writer.
  - Pi boundary: a pre-PR run with exactly one usable external report passes this workflow. Pi's phase instructions (`.pi/orchestrator/phases/implement.md:353-361`), not its extension, then require both external reports and `codex_validated: true`; the extension checks only that the state fields and history exist (`.pi/extensions/orchestrate/index.ts:545`). This change keeps both, and claims no Pi block beyond what those instructions state.
  - Inline gate: it counts its own usable reports with the AC18 check (it does not read lok's synthesis). At 0 it offers only `override` or `pause`; an override is recorded with the history action `validation_override_no_reviews`, which `orchestrate.md` and `.claude/templates/workflow-state.yaml` list. It records `codex_validated: true` only when the Codex report is usable.
- [ ] AC15: The spec-review reports are written to `docs/reviews/<slug>-spec-review-gemini.md` and `docs/reviews/<slug>-spec-review-codex.md`; the design-review reports to `docs/reviews/<slug>-review-gemini.md` and `docs/reviews/<slug>-review-codex.md`. `phases/spec.md`, `phases/design.md`, `orchestrate.md`, `design-doc/review.md`, `.claude/templates/workflow-state.yaml` and `.claude/templates/review-synthesis.md` use these names, the YAML key `review_codex` and the label "Codex". On resume, the phase files read a legacy `review_ollama` key as the second-reviewer report, so an in-flight or Pi-started workflow still resolves.
- [ ] AC16: The `implement.md` validation gate first writes `git diff main...HEAD` to `.lok/local/review-input/<slug>-branch.diff` (AC23), points the reviewers at that file and at `phases.spec.spec_file` for a specification task (at `phases.design.design_doc` and `phases.plan.plan_file` otherwise), then runs the Codex and Gemini commands of AC1 and AC2 in parallel, waits for each process by PID and keeps each exit status, writes each reviewer's output (Codex `-o`, Gemini stdout) and stderr to per-run temporary files (`mktemp`) and never directly to `docs/reviews/`, and applies the AC6 checks, including the AC18 usable-report check, to both outputs before "Display Results". It then writes `docs/reviews/<slug>-codex-validation.md` and `docs/reviews/<slug>-gemini-validation.md` per AC9 (the AC10 header and the report, or the failure-report layout) through a temporary file renamed over the target.
